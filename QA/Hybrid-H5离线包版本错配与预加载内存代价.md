# Hybrid H5 离线包版本错配与预加载内存代价

## 1. 问题背景

Hybrid H5 打开速度优化里，离线包和预加载是两个高频手段：

- 离线包可以减少 HTML、JS、CSS、图片等静态资源的网络下载耗时。
- 预加载可以提前完成 WebView 创建、资源下载、接口请求或页面渲染。

但这两个能力都不是没有代价：

- 离线包如果版本管理不严谨，容易出现 HTML、JS、CSS、Native Bridge、接口协议错配。
- 预加载如果过度，会带来明显内存上涨、CPU 消耗、接口浪费，甚至导致低端机 OOM。

所以工程上不能只追求“打开快”，还要保证“版本正确、切换安全、资源可控”。

## 2. 离线包为什么会版本错配

离线包版本错配，本质是多个版本维度没有对齐：

| 维度 | 可能的问题 |
|---|---|
| Native 容器版本 | 旧 App 不支持新 H5 需要的能力 |
| JSBridge 协议版本 | H5 调用了 Native 还没有实现的新方法 |
| H5 离线包版本 | HTML、JS、CSS 不属于同一次构建产物 |
| 接口协议版本 | H5 逻辑依赖新字段，但后端或网关未完全兼容 |
| 静态资源缓存版本 | HTML 是新的，但 JS/CSS 命中了旧缓存 |
| 灰度版本 | 灰度用户拿到了不匹配的 Native/H5/接口组合 |

典型事故包括：

- HTML 已经更新，但 JS 还是旧版本。
- JS 已经更新，但动态 chunk 没有下载完整。
- H5 调用了新的 JSBridge 方法，但用户 App 版本过低。
- 页面运行中离线包目录被覆盖，导致后续加载图片、字体、chunk 失败。
- 灰度包回滚不完整，用户本地仍然保留异常版本。

## 3. 防止版本错配的核心方案

### 3.1 Manifest 管理

离线包应该有一个明确的 `manifest`，描述这一包的完整信息：

```json
{
  "appId": "order-detail",
  "packageVersion": "1.4.2",
  "entry": "index.html",
  "minNativeVersion": "8.5.0",
  "bridgeVersion": "2.3.0",
  "resources": {
    "index.html": "sha256-xxx",
    "assets/index.a1b2c3.js": "sha256-yyy",
    "assets/index.d4e5f6.css": "sha256-zzz"
  }
}
```

这个文件至少应该包含：

- 包版本。
- 入口文件。
- 资源列表和 hash。
- 最低 Native 版本。
- JSBridge 协议版本。
- 可选的接口协议版本、灰度信息、回滚信息。

### 3.2 资源 hash 化

构建产物应该使用内容 hash：

```html
<script src="/assets/index.a1b2c3.js"></script>
<link rel="stylesheet" href="/assets/index.d4e5f6.css">
```

这样只要 JS/CSS 内容变化，文件名就变化，可以避免 WebView 缓存或本地缓存错误命中旧资源。

### 3.3 下载、解压、校验、切换分离

离线包更新不要直接覆盖当前正在使用的目录。推荐流程：

```text
1. 发现有新包 v2
2. 下载到临时目录
3. 解压到 staging_v2
4. 校验 manifest、资源 hash、入口文件完整性
5. 校验 Native 版本和 JSBridge 版本是否满足
6. 标记 v2 为 readyVersion
7. 等待安全时机切换 activeVersion
8. 延迟删除旧版本
```

核心原则：

> 下载和解压可以提前做，但真正切换 active 包，必须发生在没有页面正在使用旧包的安全时机，并且切换动作要原子化。

### 3.4 原子切换

不要把新包直接覆盖到 `current` 目录。更推荐版本目录隔离：

```text
/offline/order-detail/1.0.0/
/offline/order-detail/1.1.0/
```

本地维护一个版本指针：

```json
{
  "appId": "order-detail",
  "activeVersion": "1.0.0",
  "readyVersion": "1.1.0",
  "lastStableVersion": "1.0.0"
}
```

切换时只修改 `activeVersion`：

```text
activeVersion: 1.0.0 -> 1.1.0
```

这个动作应该是原子的，要么成功，要么失败，不应该出现半新半旧状态。

### 3.5 页面实例绑定版本

页面打开时应该绑定它使用的离线包版本：

```text
pageInstance -> appId + packageVersion
```

在页面生命周期内，所有资源都从这个版本目录读取。

即使期间新包已经下载完成，也不影响当前页面。新版本应该等下次打开页面、页面关闭后，或者 App 下次启动时再生效。

### 3.6 JSBridge 能力判断

H5 调 Native 能力之前，不能默认 Native 一定支持。基础写法：

```js
if (window.NativeBridge?.getUserInfo) {
  window.NativeBridge.getUserInfo()
} else {
  // 降级逻辑
}
```

更稳的方式是能力协商：

```js
const capabilities = await bridge.getCapabilities()

if (capabilities.includes('getUserInfoV2')) {
  bridge.getUserInfoV2()
} else {
  bridge.getUserInfo()
}
```

## 4. 全量替换离线包时，什么时机替换合适

如果公司内部当前做法是：

```text
发现新适用包 -> 下载 -> 解压 -> 替换
```

并且不是增量替换，而是全量替换，那么最重要的是不要在页面运行中覆盖当前包。

### 4.1 推荐替换时机

| 时机 | 是否适合 | 说明 |
|---|---:|---|
| App 启动后检查并后台下载 | 适合 | 只下载解压，不立即覆盖 active 包 |
| 页面打开前切换 | 适合 | 没有当前页面实例时，校验通过后切到新包 |
| 页面关闭后切换 | 很适合 | 最安全，避免运行中资源被替换 |
| App 进入后台时切换 | 可选 | 适合低风险场景，但要控制耗时 |
| 页面运行中直接覆盖 | 不适合 | 容易出现 HTML/JS/CSS 错配 |
| WebView 正在加载时覆盖 | 不适合 | 风险最高 |

### 4.2 为什么不能运行中覆盖

WebView 加载资源不是一次性全部读完，而是分阶段加载：

```text
index.html
 -> main.js
 -> chunk.js
 -> css
 -> image/font
 -> dynamic import chunk
```

如果中途替换目录，可能出现：

- HTML 是旧的，JS 已经变成新的。
- HTML 是新的，但 chunk 还没有解压完整。
- 页面运行时动态加载旧 chunk，但旧文件已经被删除。
- CSS、图片、字体资源 404。
- 旧页面继续运行，但依赖的本地资源已经不存在。

所以更稳的做法是：

```text
当前页面继续使用旧版本
新版本下载解压校验后标记为 ready
下次打开页面或页面关闭后再切换 activeVersion
旧版本延迟删除
```

## 5. 预加载有哪些类型

Hybrid 里的预加载不是一个单一动作，而是一组不同层级的优化：

| 预加载方式 | 收益 | 代价 |
|---|---|---|
| DNS/TCP/TLS 预连接 | 降低网络建连耗时 | 内存代价小，但占连接资源 |
| 离线包预下载 | 减少静态资源下载 | 占磁盘、流量 |
| WebView 预创建 | 减少容器启动耗时 | 内存明显增加 |
| 页面预渲染 | 打开接近秒开 | 内存、CPU、接口资源都高 |
| 接口预请求 | 减少数据等待 | 可能浪费请求，数据可能过期 |
| JSBridge 预初始化 | 减少初始化等待 | 增加启动阶段负担 |

越靠近“页面实例”的预加载，代价越高。

## 6. WebView 预加载的内存代价

一个 WebView 不是普通 UI 组件，它背后可能包含：

- 渲染进程。
- JS 引擎上下文。
- DOM 树。
- CSSOM。
- JS heap。
- 图片解码缓存。
- 字体缓存。
- Native 侧对象。
- JSBridge 绑定对象。
- 页面运行时状态。

所以 WebView 预创建、页面预渲染的内存成本会明显高于普通资源预下载。

预加载过度可能导致：

- App 启动变慢。
- 内存上涨。
- 低端机更容易 OOM。
- App 进入后台后更容易被系统杀。
- 多个 WebView 抢 CPU。
- 页面还没打开就发接口，浪费资源。
- 预加载页面状态过期。
- 用户没有命中预加载入口，导致收益很低。

## 7. 预加载策略如何设计

预加载要看命中率和收益比，而不是全量开启。

可以按页面价值分级：

| 页面类型 | 策略 |
|---|---|
| 高频核心入口 | WebView 预创建 + 离线包预热 |
| 中频入口 | 只预下载离线包或预连接 |
| 低频入口 | 不预加载 |
| 强实时页面 | 谨慎预请求接口 |
| 低端机 | 降级或关闭页面预渲染 |

建议配套控制策略：

- WebView 池大小限制，比如 1 到 2 个。
- App 进入后台释放预加载 WebView。
- 收到系统内存告警时释放。
- 超过一定时间未命中则释放。
- 低端机、低内存设备关闭预渲染。
- 弱网下避免大包预下载。
- 接口预请求要有过期时间和取消机制。

## 8. 面试表达

可以这样回答：

> 离线包防版本错配，我会从 manifest、资源 hash、完整性校验、原子切换和协议兼容几个层面处理。新包先下载解压到 staging 目录，校验 manifest、资源 hash、入口文件、Native 最低版本和 JSBridge 版本，校验通过后只标记为 readyVersion，不直接覆盖 active 包。真正切换一般放在页面关闭后、下次打开页面前，或者 App 下次启动时。当前已经打开的 WebView 继续绑定旧版本，新页面才使用新版本，旧版本延迟删除，避免动态 chunk、图片、字体等运行时资源被删掉。

也可以补充：

> 预加载方面，我会区分离线包预下载、WebView 预创建、页面预渲染和接口预请求。越靠近页面实例，内存和 CPU 代价越高。WebView 预创建能降低打开耗时，但会占用 JS 引擎、DOM、图片缓存和 Native 对象内存，所以一般只对高频入口做有限预热，控制 WebView 池大小，并在内存告警、后台、超时未命中时释放。预加载不是越多越好，要看命中率、收益和稳定性。

一句话总结：

> 离线包更新要保证版本组合正确，切换要原子且避开运行中页面；预加载要按页面价值分级，控制 WebView 和预渲染数量，避免为了首开速度牺牲整体内存和稳定性。
