# RAG 与代码 Agent

## RAG 是什么

RAG 是 Retrieval-Augmented Generation，通常叫“检索增强生成”。

它的核心思路是：模型不直接凭记忆回答，而是先从外部知识源里检索相关内容，再把这些内容放进上下文，让模型基于检索结果回答、总结或生成。

典型流程：

```text
用户问题
  -> 检索知识库、文档或代码片段
  -> 选出相关内容
  -> 放进模型上下文
  -> 模型生成答案
```

RAG 解决的主要问题是：模型本身不知道最新、私有或超出训练数据范围的信息在哪里。

## 代码场景里的特殊性

代码仓库和普通文档知识库不一样。普通文档更关注语义相似，代码更关注精确关系。

代码任务经常需要回答这些问题：

- 入口文件在哪里？
- 哪个函数、类型、常量才是当前业务真正使用的？
- 谁 import 了谁？
- 改这个字段会影响哪些调用方？
- 当前分支和未提交改动里有没有相关变化？
- 改完以后类型检查、单测、构建是否通过？

这些问题不能只靠向量相似度解决。

## 为什么 Codex 和 Claude Code 不主要依赖传统 RAG

Codex 和 Claude Code 都有“RAG 味道”：它们会先检索，再基于检索结果工作。但它们通常不只是传统的向量 RAG。

原因有几个。

第一，代码需要精确符号匹配。

比如：

```text
getServiceOrderDetail
SERVICE_ORDER_STATUS
RefundDestination
```

这类符号用 `rg`、类型系统、语言服务器、import 链通常比向量检索更可靠。

第二，代码关系是结构化的。

代码里有 import/export、函数调用、类型定义、路由、测试、构建配置和运行时行为。传统 RAG 拿到几个相似片段，不一定能知道真正的调用链和影响范围。

第三，公司项目变化很快。

大仓库里经常有分支差异、未提交改动、生成代码、配置开关和本地环境差异。预先构建的向量索引容易过期，而本地实时搜索可以看到当前工作区的真实状态。

第四，代码修改必须验证。

检索只提供上下文，不能证明修改是对的。代码 Agent 还需要跑类型检查、单测、lint、构建，必要时启动页面或查看浏览器结果。

第五，大仓库里相似但错误的代码很多。

同名模块、历史页面、废弃实现、测试 fixture、新旧业务并存都很常见。向量检索可能捞到“看起来相关但不该改”的片段。代码 Agent 更适合从明确入口开始追踪：

```text
路由 -> 页面 -> 组件 -> hooks/store -> API -> types -> tests
```

## 更准确的理解

狭义的传统 RAG 是：

```text
向量库检索 top-k 片段 -> 塞进上下文 -> 生成答案
```

代码 Agent 更像是：

```text
搜索工具
  + 文件读取
  + 代码结构分析
  + Shell 执行
  + Git diff
  + 类型检查和测试
  + 模型推理
```

所以，Codex 和 Claude Code 不是不用 RAG，而是把“检索”放进更大的工程闭环里。

## Codex 和 Claude Code 通常怎么做

面对几百万行代码时，Codex 和 Claude Code 都不会试图一次性理解整个仓库。它们更接近一个会使用工具的工程师，围绕当前任务逐步缩小范围。

常见流程如下：

```text
明确任务目标
  -> 搜索相关文件、符号、路由、接口、测试
  -> 读取少量高相关文件
  -> 沿 import、调用链、类型定义继续展开
  -> 修改局部代码
  -> 运行类型检查、测试、lint 或页面验证
  -> 根据报错继续迭代
```

### Codex 的方式

Codex 更强调把本地仓库当作一个可执行环境来操作。

它通常会先看 `git status`，确认当前工作区是否已有改动，避免覆盖用户正在做的事。然后用 `rg`、`rg --files`、`find`、`git diff` 等命令定位相关模块。

找到入口后，Codex 会按任务读取局部文件，例如页面、组件、hooks、API、types、constants 和测试文件。它不会把无关代码长期放进上下文，而是保留当前任务需要的事实。

修改时，Codex 会尽量贴合仓库已有风格：复用现有组件、工具函数、类型定义和目录约定。改完以后，它会优先跑能验证这次改动的命令，例如单测、类型检查、lint、构建，或者启动本地页面再用浏览器检查。

所以 Codex 的工作方式可以概括为：

```text
搜索定位 -> 局部阅读 -> 小步修改 -> 执行验证 -> 根据反馈修正
```

它的优势不在于“记住整个仓库”，而在于能持续调用工具，反复查询当前真实代码状态。

### Claude Code 的方式

Claude Code 的整体思路也类似：通过命令行工具在本地项目里搜索、阅读、修改和验证。

它通常会根据用户描述先找入口线索，比如报错栈、文件路径、组件名、接口名、路由名或测试名。然后用搜索结果建立一个小范围上下文，再沿着调用链和依赖关系继续追踪。

Claude Code 也不是单纯的“向量检索 top-k”。它会结合文件结构、命名、import/export、测试反馈和 shell 命令结果来判断下一步该看哪里、改哪里。

在大项目里，它比较依赖这些信号：

- 清晰的目录结构；
- 稳定的命名约定；
- 类型系统；
- 可运行的测试；
- 明确的报错信息；
- 用户给出的业务入口。

因此 Claude Code 的有效使用方式也不是让它“阅读整个项目”，而是给它一个可定位、可验证的任务。

### 两者的共同点

Codex 和 Claude Code 的共同点是：它们都把大仓库拆成一个个可查询、可验证的小问题。

它们主要依赖：

- 精确搜索：找文件、符号、接口、路由、测试；
- 局部上下文：只阅读当前任务真正相关的代码；
- 结构追踪：沿 import、调用链、类型定义扩展；
- 工具执行：用 shell、git、测试、构建获得反馈；
- 迭代修正：根据错误信息继续收敛。

这也是它们和传统 RAG 最大的区别：传统 RAG 主要负责“找到资料”，而代码 Agent 还要“判断关系、执行修改、验证结果”。

## 一句话总结

RAG 解决的是“模型不知道资料在哪里”的问题。

代码 Agent 还要继续解决：

- 代码关系是什么；
- 当前应该改哪里；
- 怎么避免改错旧代码；
- 改完有没有破坏现有行为。

因此，在几百万行代码的大项目里，可靠的代码 Agent 不是靠一次性读完整个仓库，而是靠检索、局部理解、调用链追踪和执行验证来逐步收敛。
