# RAG 系统中的幻觉治理

RAG 的目标不是让模型凭记忆回答，而是让模型基于检索到的资料回答。

但 RAG 仍然会产生幻觉。原因通常不只在生成阶段，也可能出现在检索、排序、上下文注入和答案校验各个环节。

可以把治理思路拆成四层：

```text
检索前：别让错问题进来
检索中：别捞错资料
生成时：别让模型离开证据
生成后：做校验和兜底
```

## 检索前：控制资料质量

很多幻觉不是模型“编”的，而是资料库本身有问题。

常见问题包括：

- 文档过期；
- 同一规则存在多个版本；
- 内容重复；
- chunk 切分破坏语义；
- 元数据缺失；
- 权限范围不清；
- 测试数据、历史废弃文档混入知识库。

治理方式：

- 清洗文档，去掉过期、重复、低质量内容；
- 建立版本、业务线、时间、文档类型等 metadata；
- 对冲突文档设置优先级；
- 控制 chunk 大小，避免切太碎或太大；
- 对生成文件、历史废弃资料、测试 fixture 建立排除规则。

如果资料本身混乱，后面 prompt 写得再好也很难稳定。

## 检索中：提高召回准确性

RAG 的幻觉很多来自“捞错资料”。

如果检索结果和问题不相关，模型就会尝试从弱相关材料里硬凑答案。

常用手段：

- hybrid search：向量检索 + BM25 关键词检索；
- metadata filter：按业务线、版本、语言、权限、时间过滤；
- rerank：对 top-k 结果重新排序；
- query rewrite：把用户问题改写成更适合检索的查询；
- 多路召回：按实体、关键词、语义相似度分别召回；
- 去重：避免相同内容反复占上下文。

对于代码、接口、字段名这类精确内容，不能只依赖向量相似度，还要结合关键词、符号、路径、类型等结构化信号。

### 多路召回和 rerank 的区别

多路召回和 rerank 不是一回事，它们处在 RAG 流程的不同阶段。

多路召回，顾名思义，就是同时用多种不同检索方式去捞候选内容，最后再把各路结果合并、去重、排序，交给 LLM 生成答案。

和它对应的是单路召回。

单路召回只用一种检索方式。最典型的是只用向量检索：

```text
用户问题
  -> 转成向量
  -> 去向量库找相似度最高的 top-k chunk
  -> 直接喂给 LLM
```

这套流程在很多场景下能跑起来，但有明显天花板。

原因是：没有任何一种检索方式是全能的。

向量检索有语义理解能力，但它也有盲区；BM25 擅长关键词匹配，但也有盲区。把多种检索方式组合起来，是为了让它们互相补盲区，让总召回质量比单路更高。

可以这样理解：

```text
多路召回
  -> 从多个入口把候选资料捞上来
  -> 目标是找得全，降低漏召回

rerank
  -> 对已经捞上来的候选资料重新排序
  -> 目标是排得准，提高最终上下文质量
```

典型流程是：

```text
用户问题
  -> query rewrite
  -> 多路召回
  -> 候选文档合并去重
  -> rerank
  -> 取 top-k
  -> 塞给模型生成答案
```

多路召回关注 recall，也就是不要漏掉可能相关的资料。

常见召回路径包括：

- 向量召回：找语义相似内容；
- BM25 召回：找关键词匹配内容；
- 实体召回：找人名、接口名、字段名、产品名；
- 路径召回：找代码路径、模块名；
- 时间或版本召回：找当前版本文档；
- 历史点击或使用召回：找高频有效资料。

rerank 关注 precision，也就是把最相关、最能回答问题的资料排到前面。

多路召回后，候选资料可能很多，质量也参差不齐。rerank 会用更强但更贵的模型或算法重新打分，判断：

- 这段资料和当前问题是否真正相关；
- 是否能直接回答问题；
- 是否比其他候选更有证据价值；
- 是否存在相似但不适用的内容。

举例：

```text
用户问题：
服务单导出失败时应该返回什么错误码？

多路召回可能捞到：
- 服务单导出接口文档
- 服务单列表页面代码
- 错误码枚举
- 导出任务状态机
- 历史导出 bug 复盘
- 订单导出文档
- 测试 fixture

rerank 后更可能排序为：
1. 服务单导出接口文档
2. 错误码枚举
3. 导出任务状态机
4. 历史导出 bug 复盘
```

一句话：

```text
多路召回解决“找得全”。
rerank 解决“排得准”。
```

## 生成时：强制基于证据回答

生成 prompt 要明确约束模型不能离开证据。

可以加入类似规则：

```text
只基于给定资料回答。
资料没有提到就说不知道。
不要补充外部常识。
关键结论必须引用来源。
如果资料冲突，要指出冲突。
不要引用不存在的内容。
```

输出最好带引用，例如：

- 文档标题；
- 段落 id；
- chunk id；
- 链接；
- 版本号；
- 更新时间。

引用机制的价值是：让每个关键结论都能追溯到资料来源。

## 允许拒答

RAG 系统一定要允许模型说“不知道”。

需要拒答或降级的情况：

- 检索分数低；
- top-k 结果互相冲突；
- 没有命中关键实体；
- 召回内容缺少答案字段；
- 文档版本不确定；
- 用户问题超出知识库范围。

这时不要强行生成看起来完整的答案，而应该说：

```text
当前资料不足，无法确认。
需要补充 xxx 文档或确认 xxx 信息。
```

高质量 RAG 不是“永远回答”，而是“有证据时回答，没证据时拒答”。

## 生成后：做答案校验

答案生成后，还可以加一层 verifier。

校验内容包括：

- 回答里的关键事实是否能在引用资料中找到；
- 数字、日期、人名、接口名、字段名是否来自原文；
- 是否引用了不存在的资料；
- 是否把多个文档的规则混在一起；
- 是否忽略了版本或权限条件；
- 输出结构是否符合 schema。

对于高风险场景，可以用第二个模型或规则程序做校验。

例如：

```text
答案
  -> 抽取关键声明
  -> 逐条回查证据
  -> 标记 unsupported / contradicted / supported
  -> unsupported 太多则拒答或要求重写
```

## 控制上下文噪音

RAG 不是塞越多资料越好。

低相关内容过多，会让模型：

- 混淆版本；
- 抓错重点；
- 引用弱相关段落；
- 把相似但不适用的规则套过来；
- 忽略真正关键的证据。

更好的做法是：

```text
少量高相关 chunk
+ 清晰来源
+ 去重
+ 按重要性排序
+ 必要时先摘要再回答
```

宁愿给 5 段强相关证据，也不要给 30 段半相关材料。

## 持续评估

RAG 系统需要专门的评估集来测幻觉。

评估问题可以覆盖：

- 答案是否有依据；
- 引用是否正确；
- 资料缺失时是否拒答；
- 多版本文档冲突时是否选对；
- 是否编造不存在的 API、字段、政策；
- 是否正确处理权限、时间、业务线条件；
- 是否能发现检索结果不足。

评估不只看答案像不像，还要看：

```text
答案是否 grounded
引用是否真实
拒答是否正确
冲突是否被识别
```

## 低成本优先级

如果资源有限，最先做的应该是：

```text
Prompt 强约束
+ 检索质量门控
```

这是成本最低、收效最快的一组组合，也是生产系统上线前必须具备的基础能力。

Prompt 强约束负责告诉模型：

- 只能基于检索资料回答；
- 资料没有提到就拒答；
- 不要补充外部常识；
- 关键结论要引用来源；
- 资料冲突时要指出冲突。

检索质量门控负责判断：

- 检索分数是否足够；
- top-k 是否命中关键实体；
- 检索结果是否互相冲突；
- 是否缺少回答所需字段；
- 是否命中了过期或低优先级文档。

如果门控不过，就不要把问题交给模型硬答，而是返回：

```text
当前资料不足，无法确认。
```

这两个能力能快速降低“检索不到也硬编”“证据不足还强答”“引用弱相关资料”的问题。

## 面试追问回答模板

如果面试官追问：“检索做好了是不是就不会幻觉？”

可以这样回答：

```text
这个想法是不对的。RAG 里的幻觉主要有两个来源：

第一，检索层没有召回到正确内容，LLM 只能靠自身知识补答案，于是容易编造。

第二，检索到了相关资料，但 LLM 在资料基础上超发挥，加入了自己的推断、常识或不受支持的结论。
```

所以，不能只靠“把检索做好”，也不能只在 prompt 里加一句“请根据资料回答”。

更完整的防控策略应该包括：

- Prompt 强约束：压制生成层幻觉；
- 检索质量门控：检索失败时直接拒答；
- 生成后引用核查：检查结论是否能回到证据；
- 结构化输出强制溯源：让每条关键结论都有据可查。

回答时可以收束成：

```text
成本最低、收效最快的是 Prompt 约束加检索门控的组合。
生产系统上线前，这两个必须做。

核心原则是：治幻觉，先治检索。
```

## 一句话总结

RAG 抗幻觉不是靠一句 prompt。

它需要一整套闭环：

```text
高质量资料
+ 精准检索
+ 证据约束
+ 可拒答机制
+ 引用校验
+ 持续评估
```

真正可靠的 RAG，不是让模型“更会编”，而是让模型每个关键结论都能落到证据上。
