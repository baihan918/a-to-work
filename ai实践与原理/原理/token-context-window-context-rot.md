# Token、上下文窗口与上下文腐化

这三个概念可以放在一条链路里理解：

```text
Token
  -> 模型读写文本的基本单位

上下文窗口
  -> 模型一次能看到的 token 总量上限

上下文腐化
  -> 上下文变长、变乱、变旧之后，模型理解和生成质量下降
```

它们共同决定了模型能看到什么、能抓住什么，以及会不会被无关信息带偏。

## Token 是什么

Token 是大模型处理文本时的基本单位，不完全等于“字”或“词”。

中文里，一个汉字可能是一个 token，也可能几个字合成一个 token。英文里，一个词可能被拆成多个 token，例如：

```text
understanding
  -> under + standing
```

模型不是直接按人类理解的句子工作，而是先把文本切成 token，再基于已有 token 预测下一个 token。

所以模型生成文本的过程可以简化成：

```text
看到前面的 token 序列
  -> 预测下一个 token
  -> 把新 token 加回上下文
  -> 继续预测下一个 token
```

这也是为什么输入越长、输出越长，通常成本越高、延迟越高。因为模型实际处理的是 token 数量，而不是人类眼里的字符数或句子数。

## 上下文窗口是什么

上下文窗口是模型一次推理时能容纳的 token 总量上限。

它不只包括用户刚发的问题，还包括：

```text
系统指令
开发者指令
用户问题
历史对话
工具调用结果
检索到的资料
代码片段
模型即将生成的回答
```

所以，一个模型支持 128k token 上下文，并不等于“可以无限聊天”。

当上下文超过上限时，系统通常需要做这些处理：

```text
截断旧消息
压缩历史
摘要关键事实
只保留最近内容
重新检索相关资料
```

上下文窗口影响的是模型当前能参考什么。重要信息如果不在窗口里，模型就不能稳定使用；重要信息如果在压缩过程中丢了细节，模型也可能只能基于不完整信息生成。

## 上下文腐化是什么

上下文腐化不是单纯指“上下文不够长”，而是指上下文质量下降。

即使内容还在窗口里，只要里面有太多无关、过期、重复或互相矛盾的信息，模型也会更容易被干扰。

常见来源包括：

```text
旧需求没有清理
废弃方案还留在历史里
工具输出太长
日志和报错混在一起
相似但错误的代码片段太多
多轮讨论里约束发生变化
压缩摘要丢失关键条件
```

上下文腐化的典型表现是：

- 忘记最新要求，去响应旧任务；
- 把已经废弃的方案当成当前方案；
- 被无关日志、历史错误或旧代码带偏；
- 回答变得摇摆、重复、啰嗦；
- 对同一个问题前后判断不一致；
- 看起来引用了上下文，实际混合了多个版本的信息。

也就是说，问题不总是“模型没看到”，有时是“模型看到了太多不该重视的东西”。

## 三者如何影响模型理解

Token 决定模型如何读取输入。

人类看到的是自然语言、段落、代码结构；模型看到的是 token 序列。模型需要从 token 序列里学习语义、语法、关系和模式。

上下文窗口决定模型当前能看到多少信息。

如果关键代码、约束、接口文档或历史决策不在上下文里，模型就只能猜。如果相关信息在上下文里，但位置很远、噪声很多，模型也可能抓不住重点。

上下文腐化决定模型看到信息之后能不能稳定判断。

当上下文里堆了过多旧信息和干扰信息，模型的注意力会被稀释，推理路径也更容易偏离当前目标。

可以这样理解：

```text
Token 影响读取粒度。
上下文窗口影响可见范围。
上下文腐化影响注意力质量。
```

## 三者如何影响模型生成

模型生成时不是一次性写完整答案，而是不断预测下一个 token。

因此，生成质量会被当前上下文强烈影响：

- 上下文里事实清楚，生成就更容易稳定；
- 上下文里约束明确，生成就更容易贴合目标；
- 上下文里噪声很多，生成就更容易混入无关内容；
- 上下文里存在矛盾，生成就可能选择错误版本；
- 上下文里缺少关键细节，生成就容易补全、猜测或幻觉。

对代码任务尤其明显。

如果上下文里同时存在旧实现、新实现、历史报错、废弃方案和用户最新要求，模型可能会把不同阶段的信息混在一起，生成一个看似合理但不符合当前代码状态的方案。

## 在代码 Agent 里的表现

代码 Agent 不能也不应该把整个大仓库一次性塞进上下文。

更可靠的方式是：

```text
明确目标
  -> 搜索入口
  -> 读取少量高相关文件
  -> 沿调用链继续展开
  -> 小范围修改
  -> 运行测试或检查
  -> 根据反馈继续收敛
```

这背后的核心原因就是上下文管理。

大仓库里相似代码很多，历史代码、测试 fixture、废弃页面、新旧业务实现经常共存。如果把太多东西放进上下文，模型不一定更聪明，反而可能被相似但错误的片段干扰。

所以代码 Agent 的关键能力不是“记住整个仓库”，而是：

- 找到当前任务真正相关的上下文；
- 避免把无关代码塞进窗口；
- 及时丢弃已经过期的推理；
- 用测试、类型检查、运行结果校正判断；
- 在多轮任务里保持最新约束优先。

## 使用模型时的实践建议

更大的上下文窗口有价值，但它不是银弹。

高质量上下文通常比大上下文更重要。

实用做法是：

- 给出明确目标和验收标准；
- 明确哪些信息是最新约束；
- 删除或说明已经废弃的方案；
- 不要一次性贴过多无关日志；
- 长任务中阶段性总结当前结论；
- 对代码任务提供入口文件、报错栈、路由、接口名或组件名；
- 让模型通过搜索、读取、验证逐步收敛，而不是一次性猜完整答案。

如果发现模型开始答非所问、引用旧结论、反复摇摆，往往不是单纯“模型不行”，也可能是上下文已经开始腐化。

这时更有效的处理方式是重新整理上下文：

```text
当前目标是什么
哪些约束仍然有效
哪些方案已经废弃
关键事实有哪些
下一步只需要解决什么
```

## 一句话总结

```text
Token 是模型处理文本的单位。
上下文窗口是模型一次能看到的范围。
上下文腐化是上下文变乱后对理解和生成造成的干扰。
```

真正影响模型表现的，不只是窗口有多大，而是当前窗口里是否装着相关、最新、清楚、可验证的信息。
