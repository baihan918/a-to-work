# System Prompt 与微调

System Prompt 和微调都能影响模型行为，但它们处在完全不同的层面。

一句话区分：

```text
System Prompt 是把规则挂在模型外面。
微调是把规则揉进模型里面。
```

也可以说：

```text
System Prompt
  -> 低成本、可配置的行为控制

微调
  -> 高成本、参数级的行为内化
```

## System Prompt 是什么

System Prompt 是模型调用时放进上下文里的高优先级指令。

它不会改变模型参数，只会影响当前对话或当前产品场景下模型如何表现。

适合放：

- 角色定位：你是客服助手、代码助手、数据分析助手；
- 安全边界：不能泄露隐私，危险操作要拒绝；
- 输出格式：必须返回 JSON，必须带引用；
- 行为规则：资料不足就拒答，不要编造；
- 工具使用规则：什么时候搜索，什么时候调用数据库；
- 当前产品约束：只基于给定资料回答；
- 任务流程：先检索，再回答；先检查代码，再修改；
- 临时策略：这次用中文、这次按某个模板输出。

它的特点是：

```text
不改模型
成本低
随时可改
可灰度
可回滚
每次调用都能注入
适合规则、边界、流程、格式
```

## 微调是什么

微调是模型训练的一种。

它不是从零训练模型，而是在已有基础模型上，用特定数据继续训练，改变模型参数，让某种能力、风格或任务模式更稳定地进入模型本身。

适合微调的内容：

- 特定客服话术风格；
- 固定问答格式习惯；
- 特定领域术语表达；
- 特定分类或抽取任务；
- 某类工单自动判断；
- 某种代码 review 风格；
- 大量相似任务的稳定输出；
- 希望少给 few-shot 也能按样例表现的任务。

它的特点是：

```text
改模型参数
成本更高
迭代更慢
需要高质量样本
需要重新评估
适合高频、稳定、大量样本的模式
适合把行为习惯和领域表达内化
```

## 很多 System Prompt 内容理论上也能微调

很多放在 System Prompt 里的东西，理论上都可以通过微调内化进模型。

例如：

- 回答风格；
- 拒答倾向；
- 引用习惯；
- 输出格式；
- 工具使用偏好；
- 客服话术；
- 代码审查口吻。

但工程上不一定值得微调。

原因是 System Prompt 更灵活：

- 改得快；
- 成本低；
- 不需要训练数据；
- 不需要重新训练；
- 不需要重新评估整个模型；
- 不同产品、客户、业务线可以共用一个模型；
- 规则变化时可以快速回滚。

所以很多时候不是“不能微调”，而是“不划算”。

## 什么时候先用 System Prompt

优先使用 System Prompt 的情况：

- 规则还在变；
- 数据不够；
- 想快速试错；
- 不同客户或业务线规则不同；
- 需要随时调整；
- 风险高，需要快速回滚；
- 只是输出格式、行为边界或工具流程。

例如：

```text
资料不足就说不知道
  -> 先放 System Prompt

回答必须带引用
  -> 先放 System Prompt 或 structured output

服务单详情页不要改 legacy 目录
  -> 放 AGENTS.md / skill，而不是微调
```

## 什么时候考虑微调

可以考虑微调的情况：

- 规则非常稳定；
- 使用频率很高；
- prompt 写很长还不稳定；
- 有足够高质量样本；
- 想减少每次 prompt 成本；
- 想让风格或模式更自然；
- 希望模型默认就具备某种习惯。

例如：

```text
客服回复要温和、简洁、有同理心
  -> 先 prompt
  -> 如果有大量优秀客服语料，可以考虑微调

代码 review 总是按固定维度输出
  -> 先 prompt / skill
  -> 如果调用量很高且格式稳定，可以考虑微调

固定工单分类任务
  -> 如果有大量标注样本，可以考虑微调
```

## 不适合优先靠微调的东西

这些不要优先靠微调：

- 最新知识；
- 经常变化的业务规则；
- 文档、政策、价格、库存；
- 私有知识库问答；
- 需要精确引用来源的答案；
- RAG 检索质量问题；
- 工具调用链路问题；
- 权限规则和临时规则。

这些更适合：

```text
RAG
memory
AGENTS.md / skill
System Prompt
工具调用
结构化输出
```

尤其是 RAG 幻觉问题，不要指望微调根治。

微调可以改善模型“怎么答”，但检索决定模型“拿什么答”。如果资料没拿对，模型再会答也可能答错。

## 判断标准

可以用三个问题判断：

```text
1. 这条规则会不会经常变？
会 -> System Prompt / RAG / skill
不会 -> 可以考虑微调

2. 需要精确引用资料来源吗？
需要 -> RAG，不靠微调

3. 是不是大量高频、稳定、可标注的模式？
是 -> 微调值得考虑
不是 -> System Prompt 更合适
```

## 一句话总结

```text
训练把能力写进权重。
System Prompt 把规则写进上下文。
微调把稳定规则和任务模式内化进模型参数。
```

工程上通常先外挂，稳定后再考虑内化：

```text
先用 System Prompt 控住行为
再用评估确认是否稳定
最后在高频、稳定、有样本、值得省 prompt 成本时考虑微调
```

更短的记忆版：

```text
System Prompt 是把规则挂在模型外面，微调是把规则揉进模型里面；先外挂，稳定后再内化。
```
