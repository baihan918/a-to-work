# AI Coding 面试准备

这份文档用于准备偏 AI 应用、AI Coding、研发效率、Agent/RAG 方向的前端岗位面试。目标不是把自己包装成算法工程师，而是讲清楚：作为资深前端，如何把 AI 能力接入真实研发流程，提升交付效率、代码质量和问题修复效率。

## 1. 核心定位

### 面试表达

我这部分实践不是单纯使用 AI 写代码，而是尝试把 AI Coding 接入团队研发链路，覆盖需求拆解、代码生成、代码 CR、Jira 问题检索、修复辅助和回归建议等环节。我的重点是找到适合 AI 介入的节点，并设计人工确认、规则约束、上下文管理和质量评估机制，让 AI 的能力真正服务研发效率和质量。

### 关键词

## 2. Agent 基础

### 要准备的点

- 工具调用
- 任务拆解
- 上下文管理
- 记忆机制
- 计划与执行
- Human-in-the-loop
- 失败重试和结果校验

### 面试问题：你怎么理解 Agent？

Agent 不是简单地调用一次大模型，而是让模型在目标约束下完成一个多步骤任务。它通常包含任务理解、计划拆解、工具调用、上下文管理、结果校验和必要的人工确认。和普通 Chatbot 相比，Agent 更强调行动能力和任务闭环。

在研发场景里，Agent 可以把一个 Jira 问题拆成多个步骤：理解问题描述、检索历史 issue、定位相关代码、分析可能原因、生成修复建议、补充测试建议。这里模型不是直接替人改代码，而是作为研发助手参与问题定位和决策。

### 面试问题：Agent 的核心难点是什么？

我认为主要有四个难点：

1. 上下文是否足够准确。代码、需求、日志、历史 issue 和规范文档如果缺失，模型很容易给出看似合理但不可靠的结论。
2. 工具调用是否可控。模型需要知道什么时候查代码、什么时候查 Jira、什么时候生成方案，而不是一直自由发挥。
3. 结果是否可验证。尤其是代码修复场景，不能只看回答是否流畅，要看能否通过测试、review 和人工确认。
4. 边界是否清晰。高风险改动、复杂业务判断、权限和资金相关逻辑不能完全交给 AI 自动处理。

### 面试问题：Human-in-the-loop 为什么重要？

在 AI Coding 场景里，AI 的输出有概率错误，尤其是代码上下文不完整、业务约束隐含、历史逻辑复杂的时候。Human-in-the-loop 的价值是把 AI 定位成建议者，而不是最终决策者。

我的理解是：AI 可以负责检索、初步分析、生成候选方案和补充检查项；开发者和 reviewer 负责确认业务语义、风险边界和最终合入。这样既能利用 AI 提效，又能控制误修和质量风险。

## 3. RAG 基础

### 要准备的点

- 文档切分
- Embedding
- 向量召回
- Rerank
- 上下文拼接
- 权限控制
- 幻觉控制
- 召回效果评估

### 面试问题：你怎么理解 RAG？
> 一种让大模型基于真实、可更新的知识来回答问题的技术方案,它和微调、Prompt Engineering 等技术是互补的，而不是替代关系。

RAG 是 Retrieval-Augmented Generation，也就是先从外部知识库里检索相关资料，再把检索结果作为上下文交给大模型生成答案。它解决的是模型本身不知道企业内部知识、项目代码、历史 issue 和业务规则的问题。

在研发效率场景里，RAG 可以把 Jira、技术文档、代码规范、历史故障复盘、组件使用说明等资料接入 AI，让模型回答问题或生成修复建议时有更可靠的依据。

### 面试问题：RAG 的基本流程是什么？

基本流程可以分成六步：

1. 数据接入：把文档、Jira、代码片段、规范等数据收集进知识库。
2. 文档切分：按语义边界切 chunk，避免太长导致噪声过多，也避免太短丢失上下文。
3. 向量化：用 embedding 模型把文本转成向量。
4. 召回：根据用户问题检索相似内容。
5. 重排：用 rerank 或规则过滤提升相关性。
6. 生成：把高相关内容拼进 prompt，让模型基于证据回答。

### 面试问题：RAG 怎么减少幻觉？

可以从几个层面控制：

1. 提升召回质量，保证上下文里有真正相关的信息。
2. 在 prompt 里要求模型基于检索内容回答，缺少依据时明确说不确定。
3. 给结果加引用来源，比如关联到具体 Jira、文档或代码文件。
4. 对高风险输出设置人工确认，不让模型直接执行。
5. 建立 case 集评估，持续观察错误回答、漏召回和误召回。

### 面试问题：代码场景里的 RAG 有什么特殊点？

代码场景不能只按普通文档处理。代码有模块边界、调用关系、类型定义、历史变更和业务语义。只做文本相似度可能找不到真正相关的代码。

所以代码 RAG 最好结合多种上下文：文件路径、模块归属、函数调用、commit 历史、Jira 关联、组件依赖和业务文档。这样模型定位问题时，不只是匹配关键词，而是更接近真实研发排查路径。

## 4. LLM 评测

### 要准备的点

- 准确率
- 采纳率
- 误判率
- 漏检率
- 人工评审
- Case 集
- 基准集
- 灰度验证

### 面试问题：AI Coding 的效果怎么评估？

我不会只用“感觉变快了”来评估，而是会拆成效率、质量和采纳三个方向。

效率上看问题定位耗时、需求开发耗时、CR 耗时有没有下降。质量上看 AI CR 提前发现的问题数量、误判率、漏检率、线上缺陷是否减少。采纳上看 AI 建议有多少被开发者或 reviewer 采纳，哪些建议被拒绝，以及拒绝原因是什么。

### 面试问题：怎么设计评测 case 集？

我会从真实研发场景里抽取 case，而不是只构造理想样例。比如：

1. 常规业务需求拆解 case。
2. React Hooks 依赖缺失 case。
3. 类型定义不完整 case。
4. Jira 问题描述模糊 case。
5. 历史 issue 可复用 case。
6. AI 容易误判的复杂业务逻辑 case。

每个 case 要有标准答案或人工评审结论，用来判断 AI 是否正确识别问题、是否给出有效建议、是否遗漏关键风险。

### 面试问题：采纳率和准确率哪个更重要？

两者都重要，但含义不同。准确率衡量 AI 识别和建议是否正确，采纳率衡量 AI 输出对真实研发是否有用。

如果准确率高但采纳率低，说明建议可能不符合团队流程或成本太高。如果采纳率高但准确率不稳定，说明存在质量风险。实际落地时，我会同时看准确率、采纳率、误判率和人工反馈，避免只用单一指标判断效果。

## 5. AI Coding 流程图

### 目标流程

```text
需求理解
  -> 任务拆解
  -> Vibe Coding 生成代码初稿
  -> 开发者调整和补充业务逻辑
  -> AI Code Review
  -> 人工 Code Review
  -> Jira 问题检索和修复辅助
  -> 测试建议和回归清单
  -> 人工确认上线
```

### 面试问题：你们怎么把 AI Coding 接入研发流程？

我会把 AI 介入点拆成三个阶段。

第一阶段是编码前，主要用于需求理解、任务拆解和技术方案初稿。这里 AI 帮助开发者把需求转成组件拆分、状态设计、接口依赖和边界 case。

第二阶段是编码和 CR，主要用于 Vibe Coding 生成初稿，以及 AI CR 检查 diff、Hooks 依赖、类型问题、潜在重复渲染、边界 case 和测试建议。

第三阶段是问题修复，结合 Jira 描述、历史 issue、日志和代码上下文，辅助定位相关模块和可能原因，生成修复建议和回归范围。

整个流程里，AI 的定位是辅助分析和建议生成，最终合入和关键判断仍然由开发者和 reviewer 确认。

### 面试问题：Vibe Coding 怎么落地才不失控？

我会先限定适用场景。适合 AI 生成的是重复性较高、边界清晰、上下文充分的代码，比如常规页面、表单、组件初稿、类型定义、测试样例和样板逻辑。不适合的是复杂业务决策、资金安全、权限边界、历史包袱很重的逻辑。

落地上会要求 AI 先输出方案和拆解，再生成代码；生成后开发者必须检查组件边界、状态设计、异常分支、类型完整性和测试覆盖。这样可以避免 AI 在上下文不足时直接写出一大段看似可用但风险很高的代码。

### 面试问题：AI CR 主要检查什么？

AI CR 适合做低成本、高重复、规则明确的检查，比如：

- Hooks 依赖是否缺失。
- 是否存在明显重复渲染风险。
- TypeScript 类型是否过宽或缺失。
- 是否遗漏 loading、empty、error 状态。
- 是否存在边界 case。
- 是否违反团队组件或接口规范。
- 是否需要补充测试或回归范围。

我不会把 AI CR 当成替代人工 review，而是把它作为前置检查，让 reviewer 少花时间在低级问题和重复性检查上，把精力放在业务正确性和架构判断上。

### 面试问题：Jira 查找和修复辅助怎么做？

Jira 场景可以分成四步：

1. 解析问题描述，提取业务场景、错误表现、影响范围和关键字段。
2. 检索历史 Jira、文档、日志和相关代码模块。
3. 生成可能原因和排查路径，给出候选修复点。
4. 输出修复建议、风险点和回归清单，由开发者确认。

这里的关键不是让 AI 自动改代码，而是缩短定位路径，帮助开发者更快找到相关模块、历史相似问题和可能的修复方向。

## 6. 常见追问

### 这是不是只是套了一层 AI？

不是。单纯套 AI 是把问题丢给模型，然后复制结果。真正的工程落地要处理上下文、流程、质量和评估。

我关注的是：在哪些研发节点接入 AI、提供什么上下文、输出如何约束、怎么人工确认、如何评估效果、哪些场景禁止自动化。只有这些机制建立起来，AI 才能稳定服务团队研发，而不是停留在个人工具使用。

### 如果 AI 给错建议怎么办？

首先要承认 AI 一定会出错，所以不能把它放在无人工确认的高风险链路里。

我的处理方式是：低风险建议可以让 AI 自动生成，比如测试建议、风险提示、候选排查路径；涉及代码合入、业务逻辑和线上风险的内容必须人工确认。同时通过 case 集、误判记录和 review 反馈持续优化 prompt、规则和知识库。

### 怎么证明这个项目有价值？

我会从三个角度证明：

1. 效率：需求拆解、代码初稿、问题定位和 CR 耗时是否下降。
2. 质量：AI CR 是否提前发现低级问题、边界遗漏和类型风险。
3. 协作：新人排查成本是否下降，reviewer 是否减少重复性检查负担。

如果有数据，可以直接给出前后对比；如果暂时没有完整数据，也可以用真实案例说明 AI 在具体环节节省了哪些步骤和时间。
