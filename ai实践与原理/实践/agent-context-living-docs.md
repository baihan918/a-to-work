# Agent 上下文是活文档

`CLAUDE.md`、Codex skill、项目约定文档和业务域说明，不应该被当成一次性写完的说明书。

它们更像一组持续打磨的协作协议：Agent 每做错一次，如果这个错误有复用价值，就应该把原因和修正方式沉淀到对应位置里。

## 为什么要持续维护

Agent 做错，通常不是单点问题，而是上下文里缺了某条稳定规则。

常见情况包括：

- 不知道某个目录不能手改；
- 没有复用项目已有组件；
- 跑错测试命令；
- 忽略了业务域里的特殊状态；
- 改了旧页面而不是当前入口；
- 不知道接口字段的真实含义；
- 没有检查用户已有未提交改动。

这些问题如果只在一次对话里解释，下次还可能再犯。更好的做法是把它变成可复用规则。

## 沉淀到哪里

不要把所有教训都塞进全局文档。应该按影响范围放到对应位置。

```text
全局协作偏好
  -> 放到全局规则或通用 skill

项目启动、目录、验证命令
  -> 放到项目级 README、AGENTS.md、CLAUDE.md 或 Codex 项目说明

前端组件、样式、交互、测试约定
  -> 放到 frontend skill 或前端约定文档

后端接口、数据库、错误处理、服务分层
  -> 放到 backend skill 或后端约定文档

具体业务域规则
  -> 放到业务域 skill 或业务 md
```

核心原则是：谁会再次用到这条规则，就放到谁会被触发读取的地方。

## 怎么写修正规则

沉淀内容要短、准、可执行。

不推荐写：

```text
以后要注意服务单逻辑。
```

推荐写：

```text
修改服务单详情页按钮时，先确认当前入口是 `src/pages/service-order/detail`，不要改历史页面 `src/legacy/service-order`。
```

好的规则通常包含：

- 触发场景：什么时候需要看这条；
- 正确做法：应该怎么做；
- 错误边界：不要做什么；
- 验证方式：改完跑什么命令或检查什么页面。

## 错误复盘模板

可以用这个结构记录：

```md
## 规则标题

触发场景：
当修改 xxx 时。

正确做法：
优先使用 xxx，沿 xxx 查找入口。

不要这样做：
不要修改 xxx，因为它是旧实现或生成文件。

验证方式：
运行 xxx，或检查 xxx 页面。

来源：
某次 Agent 曾因为 xxx 做错，所以补充这条规则。
```

## 维护节奏

不是每个错误都值得沉淀。只有满足下面任一条件时，才应该写进 skill 或 md：

- 以后很可能再遇到；
- 错误代价比较高；
- 规则足够稳定；
- 它能帮助 Agent 更快定位入口；
- 它能减少重复解释。

如果只是一次性需求、临时方案、还没验证的猜测，不要写进长期规则。长期上下文要保持干净，否则会变成新的噪音。

## 一句话总结

Agent 上下文不是越多越好，而是要随着真实错误持续修剪和补强。

每次 Agent 做错，都可以问一句：

```text
这是一次性失误，还是缺少一条以后也会用到的规则？
```

如果是后者，就把它沉淀到对应的 skill 或 md 里。
