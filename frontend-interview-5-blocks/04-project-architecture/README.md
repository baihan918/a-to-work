# 04 项目架构

## 高频面试题

### 1. 复杂页面怎么拆组件？

**答题口径**

先按业务职责拆，而不是按视觉块机械拆。通常可以分为页面容器、查询区、列表区、详情区、操作区、弹窗区、通用 hooks 和服务层。

页面容器负责数据编排和状态连接，展示组件负责 UI，业务组件负责特定场景逻辑，服务层负责接口和数据转换。

**注意点**

- 不要让所有状态堆在一个大组件里。
- 不要把接口字段直接扩散到所有组件。
- 组件拆分要服务于变化边界。

### 2. 复杂表单怎么设计？

**答题口径**

表单状态可以分为字段值、校验状态、异步状态、联动状态、提交状态。简单表单用受控即可，复杂表单可以用表单库、schema 配置、局部状态隔离。

跨字段联动要集中管理，异步校验要处理竞态和取消。

**注意点**

- 不要每个字段都向顶层频繁 setState。
- 大表单要考虑分区渲染和局部更新。
- 校验规则要区分同步、异步、提交前、实时校验。

### 3. 权限体系怎么设计？

**答题口径**

权限通常分为路由权限、菜单权限、按钮权限、接口权限和数据权限。前端负责展示和交互控制，后端负责最终安全校验。

前端可以在路由层做准入，菜单层做过滤，按钮层做操作控制，请求层处理无权限响应。

**注意点**

- 前端权限不能当安全边界。
- 权限判断要收敛，不要散落在 JSX 里到处写 if。

### 4. 请求层怎么设计？

**答题口径**

请求层要统一 baseURL、鉴权、错误处理、超时、取消、重试、埋点、响应转换。业务层不应该到处处理 token 过期和通用错误。

复杂项目还要区分 server state 和 client state，请求缓存可以交给 React Query、SWR 或内部数据层。

**注意点**

- 不要把接口原始结构直接透传到 UI。
- 要处理重复请求、竞态、取消和幂等。

### 5. 状态管理怎么选型？

**答题口径**

先区分状态类型：

- 本地 UI 状态：组件内部 `useState`。
- 复杂流程状态：`useReducer` 或状态机。
- 跨组件共享状态：Context、Zustand、Redux 等。
- 服务端状态：React Query、SWR 或请求缓存层。

选型看共享范围、更新频率、调试需求、团队熟悉度和长期维护。

**注意点**

- 不要所有状态都放全局。
- Context 高频更新会拖动订阅组件渲染。
- 服务端数据不要和客户端 UI 状态混在一起。

### 6. 多状态联动怎么避免混乱？

**答题口径**

把状态流转建模，不要堆多个互相触发的 `useState`。可以用 reducer、状态机、派生状态、事件驱动方式。

原则是：能计算出来的不要重复存；状态变化通过明确 action 触发；副作用集中在边界处理。

**注意点**

- 多个 effect 互相 setState 是混乱来源。
- 派生状态重复存会导致不一致。

### 7. 如何设计可复用业务组件？

**答题口径**

先沉淀稳定业务场景，不要过早抽象。组件 API 要表达业务意图，扩展点要明确。通用能力通过 props、slots、render props 或组合暴露，变化大的逻辑留给外部。

**注意点**

- 避免万能组件。
- 避免大量布尔 props。
- 文档和示例比抽象本身更重要。

### 8. 微前端适合什么场景？

**答题口径**

微前端适合多个团队独立交付、技术栈或发布节奏不同的大型系统。它解决组织协作和独立发布问题，不是性能优化银弹。

核心问题包括应用隔离、路由协调、样式隔离、依赖共享、通信、权限、监控、部署。

**注意点**

- 单团队小系统不要轻易上微前端。
- 微前端会增加运行时和治理复杂度。

### 9. 前端稳定性怎么治理？

**答题口径**

稳定性包括预防、发现、定位、恢复。预防靠类型、测试、规范、代码评审。发现靠错误和性能监控。定位靠 sourcemap、用户链路、版本关联。恢复靠灰度、回滚、降级和开关。

**注意点**

- 只说 ErrorBoundary 不够。
- 要能讲发布流程、监控和降级策略。

### 10. 如何从业务项目里提炼架构价值？

**答题口径**

不要只讲“做了页面”，要讲复杂度和治理动作。例如：

- 状态复杂：如何建模。
- 权限复杂：如何收敛。
- 性能差：如何定位和优化。
- 重复开发多：如何组件化和配置化。
- 线上问题多：如何监控和质量门禁。

## 三个必备项目故事

### 复杂页面故事

> 背景是页面包含筛选、列表、详情、批量操作、权限和多状态流转。问题是状态分散、联动混乱。我把状态分为服务端数据、UI 状态和流程状态，服务端数据交给请求缓存，UI 状态局部维护，流程状态用 reducer 收敛。组件按查询、列表、详情、操作区拆分，权限判断统一封装。结果是新增需求主要增加 action 和局部组件，不再全页面改状态。

### 性能优化故事

> 页面卡顿后，我先用 React Profiler 定位重复渲染，再用 Performance 看主线程长任务。发现输入筛选会拖动整张表重渲染。我拆分输入状态和查询状态，用虚拟滚动减少 DOM 数量，稳定 columns 和 handlers，并 memo 行组件。优化后 commit 时间和交互延迟明显下降。

### 工程化提效故事

> 团队多个页面重复实现权限、请求错误处理和状态流转。我把这些横切逻辑沉淀为请求层、权限 hook、业务组件和页面模板，并接入 lint、typecheck、监控和发布检查。收益是新页面开发成本下降，线上同类问题减少。
