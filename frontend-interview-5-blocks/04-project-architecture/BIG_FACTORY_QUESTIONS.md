# 项目架构：大厂追问题库

## 字节风格

### 1. 讲一个你做过最复杂的前端项目，复杂在哪里？

**题解口径**

不要从页面大开始讲，要从复杂度来源讲：业务流程多、状态联动多、权限复杂、数据量大、性能要求高、多人协作、发布风险高。然后讲你的建模、拆分、治理和结果。

**推荐结构**

背景、复杂度、你的角色、方案、取舍、结果、复盘。

### 2. 如果一个页面很多 useEffect 互相触发，怎么治理？

**题解口径**

先识别哪些是派生状态，能计算的不要存。把状态变化收敛成明确 action，用 reducer 或状态机管理流程。副作用集中在边界，比如请求、订阅、埋点。避免 A effect set B，B effect set C 的链式混乱。

### 3. 权限、状态、请求都耦合在页面里，怎么重构？

**题解口径**

先分层：权限判断收敛为 hook 或服务，请求封装到 service/data layer，状态按 UI、server、flow 分层。重构顺序不要大爆炸，先抽横切逻辑，再拆组件，再补测试或监控。

### 4. 你如何判断一个组件该不该抽象？

**题解口径**

看变化是否稳定、重复是否真实、抽象后 API 是否更简单、是否降低维护成本。两三个相似场景不一定要抽象，可能先复制更好。抽象应该服务于变化边界，不是消除所有重复。

### 5. 如果列表支持筛选、排序、分页、批量操作、实时刷新，状态怎么设计？

**题解口径**

查询条件、分页排序、选中态、数据缓存、刷新状态、批量操作状态分开管理。查询参数可作为服务端状态 key，选中态要考虑翻页和数据刷新后是否保留。批量操作要处理权限、失败项、乐观更新或重新拉取。

## 蚂蚁 / 阿里风格

### 1. 中后台复杂表单如何架构？

**题解口径**

字段值、校验、联动、权限、异步数据、提交状态分层。规则复杂时可以 schema 化，但 schema 不要变成不可调试的黑盒。表单组件要支持局部渲染、异步校验取消、草稿、回显、权限禁用。

### 2. 业务组件和基础组件边界怎么划？

**题解口径**

基础组件不理解具体业务，只表达交互原语和设计规范。业务组件封装稳定业务场景，例如带权限的操作栏、业务表格、状态流转组件。跨业务差异大时提供组合能力，不要塞入过多分支。

### 3. 如何设计请求错误处理体系？

**题解口径**

请求层处理通用错误、登录过期、权限、网络异常、超时和重试。业务层处理领域错误和用户决策。页面层提供错误态、空态和重试入口。监控层记录接口、版本、用户链路和错误上下文。

### 4. 如何保证大型项目多人协作不失控？

**题解口径**

模块边界清晰、公共能力收敛、类型约束、代码规范、组件文档、review checklist、CI 门禁、owner 机制、技术债定期治理。关键是让正确做法更容易。

### 5. 低代码 / 配置化平台怎么避免失控？

**题解口径**

配置化适合稳定模式，不适合所有业务。要设计 schema 版本、扩展点、校验、预览、回滚、权限、监控和逃生口。复杂逻辑可以插件化，不要把所有逻辑塞进 JSON。

### 6. 项目架构题的高分回答模板

> 这个项目的难点不是页面多，而是状态、权限和流程交织。我的处理是先做领域建模，把状态分成服务端数据、UI 状态和流程状态；再做组件边界拆分，让页面容器负责编排，业务组件负责场景，基础组件负责 UI；最后补请求层、权限层和监控。这个方案的取舍是前期设计成本更高，但后续新需求主要在局部扩展，降低了回归风险。
