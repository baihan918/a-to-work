# 06 AI 落地与工程化

## 面试会不会问 AI？

会问，而且 2026 年前端面试里越来越常见。但不同岗位深度不同。

普通前端岗通常不会深问模型训练原理，更关注你有没有把 AI 能力接进真实产品。AI 产品前端、AI 工程化前端、Agent / 全栈岗位会继续追问 RAG、tool calling、Agent、eval、trace、权限和成本。

9 年前端的合理定位不是“我懂模型训练”，而是：

> 我能把 AI 能力工程化落到业务产品里，负责前端交互、流式体验、工具调用展示、权限边界、错误兜底、质量监控和成本/延迟优化。

## 岗位分层：不同岗位需要掌握什么？

下面按真实大厂和 AI 产品团队常见面试侧重点拆。越往后，越从“前端接入能力”升级到“AI 系统 owner 能力”。

### 1. 普通前端岗：AI 功能接入与体验实现

**岗位画像**

主职责还是 React / 前端工程。AI 是业务功能的一部分，例如智能客服、文案生成、知识库问答、报表解读、代码解释、运营助手。

这类岗位一般不会深问模型训练、Transformer 数学细节，但会问你能不能把 AI 能力稳定接到页面里。

**必须掌握**

- LLM API 基本调用链路。
- 前端不能直接暴露模型 key。
- SSE 流式输出。
- WebSocket 与 SSE 的选择。
- 打字机效果、增量渲染。
- 停止生成、重新生成、失败重试。
- AI 消息状态机：生成中、完成、失败、取消。
- Markdown 渲染、代码高亮、XSS 防护。
- JSON 结构化输出的前端校验。
- 对话历史和上下文展示。
- token 太长时的前端体验处理。
- loading、骨架屏、空态、错误态。
- 用户反馈：点赞、点踩、复制、重新生成。

**需要能讲清**

- 为什么 AI 输出要流式展示？
- SSE 和 WebSocket 怎么选？
- Markdown 为什么不能直接 `innerHTML`？
- 用户点击停止生成，前后端分别要做什么？
- AI 返回 JSON 不合法怎么办？
- 如何避免生成过程频繁 setState 导致页面卡？

**常见真题风格**

1. 如何实现 ChatGPT 那种逐字输出？
2. SSE 和 WebSocket 区别，AI 对话你选哪个？
3. 大模型返回 Markdown，前端怎么安全渲染？
4. AI 生成中用户切换页面，怎么处理请求？
5. 如何实现停止生成？
6. AI 接口很慢，前端体验怎么优化？
7. AI 输出代码块，怎么做增量渲染和高亮？

**项目证据**

你至少要能拿出一个 AI 交互项目，讲清：

- 接口链路。
- 流式渲染。
- 状态设计。
- 异常兜底。
- 安全渲染。
- 用户反馈。

**面试定位话术**

> 我不是只会调接口，而是能把 AI 输出这种不确定、流式、可能失败的结果，做成用户可理解、可中断、可重试、可追踪的产品体验。

### 2. AI 产品 / AI 工程化前端岗：AI 链路、质量与平台化

**岗位画像**

你不只是做页面，而是参与 AI 产品链路设计。常见方向包括企业知识库问答、智能运营平台、Agent 控制台、AI 工作台、低代码 AI 编排、内部 Copilot。

这类岗位会明显追问 RAG、tool calling、Agent 过程展示、评估、监控、权限和成本。

**必须掌握**

- RAG 基本链路：chunk、embedding、vector DB、retrieval、rerank、context 拼接。
- RAG 与 fine-tuning 的区别。
- 引用来源展示和答案可追溯。
- tool calling / function calling 基本机制。
- 工具调用参数校验、权限校验、失败重试。
- Agent 事件流展示：计划、工具调用、观察结果、最终回答。
- AI trace：一次生成中的 prompt、retrieval、tool call、model output。
- eval 基本概念：golden set、人工标注、LLM-as-judge、回归测试。
- 成本指标：输入 token、输出 token、模型单价、缓存命中率。
- 延迟指标：首 token 时间、总生成时间、工具调用耗时。
- 安全：prompt injection、数据脱敏、权限过滤。
- 多模型 fallback 和降级策略。

**需要能讲清**

- 为什么企业知识库问答通常用 RAG，而不是直接微调？
- RAG 命中不准，可能是哪几层的问题？
- 前端如何展示引用来源，降低幻觉风险？
- tool calling 和普通接口调用有什么区别？
- Agent 失败时，怎么定位是检索错、工具错、模型错还是权限错？
- AI 质量如何监控？不能只看接口 200。
- 如何控制 token 成本和延迟？

**常见真题风格**

1. 设计一个企业内部知识库问答系统。
2. RAG 和 fine-tuning 怎么选？
3. 如果用户问的问题检索不到资料，系统应该怎么答？
4. 如何展示 AI 的引用来源？
5. tool calling 的参数能不能直接执行？为什么？
6. Agent 调工具失败，前端和后端分别怎么处理？
7. 如何做 AI 功能的质量评估和线上监控？
8. 如何防止用户通过 AI 查到无权限数据？
9. 如何降低大模型接口成本？
10. 如何做 prompt / 模型版本回滚？

**项目证据**

最好准备一个“AI 产品工程化”故事：

- RAG 或工具调用链路。
- 前端如何展示过程和来源。
- 权限如何处理。
- 质量如何评估。
- 成本和延迟如何监控。
- 线上失败如何定位。

**面试定位话术**

> 我能参与 AI 产品从 demo 到生产的工程化闭环。前端不仅展示答案，还要展示过程、引用、工具状态和错误恢复；工程上要有 trace、eval、权限、成本和延迟监控。

### 3. AI Engineer / 全栈 Agent 岗：AI 系统设计与生产级 Agent

**岗位画像**

这类岗位已经不是传统前端，而是 AI 应用系统 owner。可能要求 Python / Node 后端、LLM API、RAG、Agent orchestration、eval、observability、云服务、数据库、队列、权限和部署。

面试会更像系统设计 + AI 工程 + 一部分模型原理。不会只问“怎么调接口”，而是问你如何让 Agent 在生产环境可靠工作。

**必须掌握**

- LLM API 语义：messages、system prompt、temperature、top_p、max tokens、structured output。
- Prompt 设计和版本管理。
- RAG 架构设计和评估。
- embedding 模型选择、chunk 策略、向量库、混合检索、rerank。
- Agent loop：plan、act、observe、reflect、stop condition。
- ReAct / plan-and-execute 基本思想。
- tool calling 协议、参数 schema、权限、安全执行。
- 多步任务的状态管理、重试、幂等、超时和补偿。
- memory：短期上下文、长期记忆、用户偏好、任务状态。
- eval：任务成功率、检索命中率、faithfulness、tool-call accuracy。
- observability：trace、span、日志、prompt、retrieved chunks、tool input/output。
- 生产运维：灰度、回滚、限流、熔断、fallback、成本预算。
- 安全：prompt injection、越权访问、数据泄露、工具滥用。
- 基础模型原理：Transformer、attention、token、embedding、上下文窗口。

**需要能讲清**

- 设计一个能查资料、调用工具、完成任务的 Agent 系统。
- Agent 如何避免无限循环？
- tool call 失败如何重试？什么时候不能重试？
- 如何评估一个 Agent 是否真的完成任务？
- RAG 系统回答错了，如何定位是检索问题还是生成问题？
- 如何做端到端 trace 回放？
- 如何设置成本和延迟预算？
- 如何防 prompt injection？
- fine-tuning、RAG、prompt engineering、tool calling 分别适合什么问题？
- 多 Agent 是否必要？什么时候反而增加复杂度？

**常见真题风格**

1. 设计一个客服 Agent，可以查订单、改地址、创建工单。
2. 设计一个企业知识库 RAG 系统，要求有引用和权限隔离。
3. 设计一个代码审查 Agent，如何调用工具和评估结果？
4. tool calling 参数由模型生成，如何保证安全？
5. Agent 执行 10 步后还没完成，怎么办？
6. RAG 召回了错误文档，如何发现和修复？
7. 如何建立 golden set 做回归评估？
8. 如何观测一次 Agent run 的完整链路？
9. 如何在成本降低 50% 的情况下保持质量？
10. 什么时候选择微调，什么时候选择 RAG？

**项目证据**

需要准备系统级项目故事：

- 业务目标。
- 架构图。
- 模型、RAG、工具、权限、存储、队列、监控。
- 失败场景和恢复策略。
- eval 指标和线上数据。
- 成本、延迟、质量的权衡。

**面试定位话术**

> 我能把 LLM、RAG、tool calling、Agent loop 和工程基础设施组合成可上线系统。重点不是 demo 能跑，而是任务可完成、过程可追踪、质量可评估、权限可控、成本可预测、失败可恢复。

## 准备优先级

如果你目标还是 9 年前端，但想增强 AI 差异化，优先准备：

1. 普通前端岗全部能力。
2. AI 工程化前端里的 RAG、tool calling、trace、eval、权限、成本。
3. AI Engineer 岗里只补基础原理和系统设计，不要一开始深挖模型训练。

你的最优叙事是：

> 我是前端出身，但不是只做 AI 页面。我能把流式交互、RAG 来源展示、工具调用过程、权限边界、质量反馈和监控闭环串起来，推动 AI 功能从 demo 变成生产能力。

## 结合两个 JD 的定向准备

这两个 JD 都不是纯“普通前端”。它们更接近 **AI 产品 / AI 工程化前端岗**，但侧重点不同：

- 货架 AI 应用方向：偏电商导购、Agent 框架、LLM 应用架构、产品研发、工程质量、数据评测。
- 创新方向：偏跨端架构、React Native、小程序、AI Coding、互动渲染、工程化和性能稳定性。

你的准备要围绕“AI 应用产品研发 + 前端工程架构”来讲，而不是只讲 React 页面。

### JD 1：货架 AI 应用方向

**岗位关键词**

- 客户端应用架构。
- Agent 框架。
- 产品体验和性能优化。
- 质量风险把控。
- 电商 AI 导购场景。
- AI 框架研究、工程研发、产品设计协作。
- AI 技术调研和场景落地。
- LLM 应用架构。
- PE 工程化。
- 数据评测。
- Agent、RAG、LangChain。

**面试官真正想看什么**

这个岗位不是只找会写页面的人，而是找能把“AI 导购”从想法变成产品能力的人。

你需要证明：

- 你懂电商导购业务：用户意图、商品理解、推荐、比价、决策辅助、转化路径。
- 你懂 AI 应用链路：意图识别、RAG、工具调用、Agent 编排、结构化输出。
- 你懂前端产品体验：流式输出、卡片化商品展示、对话式导购、失败兜底。
- 你懂工程质量：性能、稳定性、埋点、灰度、降级、监控。
- 你懂协作：能和产品、算法、后端一起拆方案和推进落地。

**必须准备的能力点**

1. AI 导购产品链路
   - 用户输入理解。
   - 商品知识检索。
   - 商品召回和排序。
   - 对话式澄清。
   - 商品卡片推荐。
   - 购买决策辅助。
   - 用户反馈闭环。

2. Agent 框架基础
   - Agent loop：plan、act、observe、final。
   - tool calling：查商品、查库存、查优惠、查评价、查物流。
   - 最大步数、超时、失败重试。
   - 高风险动作用户确认。

3. RAG 和知识检索
   - 商品知识、活动规则、FAQ、评价摘要。
   - chunk、embedding、vector search、rerank。
   - 引用来源和答案可追溯。
   - 权限和数据边界。

4. 数据评测
   - 导购回答准确率。
   - 商品推荐相关性。
   - 幻觉率。
   - 工具调用成功率。
   - 首 token 时间。
   - 总生成耗时。
   - 转化率、点击率、加购率。

5. 前端工程架构
   - 对话状态机。
   - 商品卡片组件化。
   - 流式消息 + 结构化事件渲染。
   - 异常态、重试、停止生成。
   - 埋点和 trace。

**高频面试题**

1. 如果让你设计一个电商 AI 导购助手，你会怎么做？

答题要点：

> 我会把它拆成前端交互层、AI 编排层、业务工具层和评估监控层。前端负责对话、商品卡片、流式状态和用户反馈；AI 编排层负责意图识别、RAG 检索、tool calling 和多轮上下文；业务工具层提供商品搜索、库存、优惠、评价、订单等能力；评估层看推荐相关性、工具调用成功率、幻觉率、转化指标和成本延迟。

2. AI 导购为什么需要 tool calling？

答题要点：

> 商品价格、库存、优惠、订单状态这些是实时业务数据，不能只靠模型记忆。模型负责理解意图和组织回答，真实数据通过工具查询。工具调用前要校验参数和权限，结果返回后再由模型生成可读答案或由前端结构化展示。

3. AI 导购为什么需要 RAG？

答题要点：

> 商品知识、活动规则、导购话术、售后政策更新频繁，不适合靠模型参数记忆。RAG 可以把最新资料检索出来给模型使用，回答更可追溯，也更容易更新和评估。

4. 如何评估 AI 导购效果？

答题要点：

> 不能只看回答“像不像”。要分层看：检索命中率、推荐相关性、工具调用成功率、事实准确率、幻觉率、首 token 时间、总耗时、用户点赞/点踩、商品点击、加购、转化。上线前用 golden set 回归，上线后用真实用户反馈和业务指标持续评估。

5. 前端在 AI 导购里有哪些关键难点？

答题要点：

> 难点是 AI 输出不确定、流式、可能失败。前端要把 token 流、工具调用事件、商品卡片、引用来源、错误态、停止生成和重试统一成状态机；还要保证渲染性能，避免每个 token 都触发重布局；同时埋点记录用户行为和 AI trace。

**项目包装模板**

> 我可以把过往复杂业务页面经验迁移到 AI 导购场景：复杂页面里的状态流转、权限、请求、性能优化，对应到 AI 导购里的会话状态机、工具调用、商品卡片、流式渲染和监控闭环。我的优势不是只调模型接口，而是能把 AI 能力落到一个可用、可评估、可迭代的电商产品链路里。

### JD 2：创新方向 / React Native / AI Coding

**岗位关键词**

- 小红书创新业务核心场景。

- 高性能、高可用。
- 模块化架构。
- AI Coding 探索。

3. AI Coding

   - 研发流程中的质量门禁。
   - AI 生成代码的安全和正确性校验。

4. AI Agent 与互动体验
   - Agent 辅助创作。

   - 多模态输入：文本、图片、语音。
   - 互动渲染：动态内容、实时反馈、生成式 UI。
   - 用户可控和可编辑。

5. 工程化
   - 模块化架构。
   - 组件库。
   - 构建优化。
   - 监控告警。
   - 自动化测试。
   - CI/CD。

**高频面试题**

1. React Native 和 H5 / 小程序怎么选？

答题要点：

> H5 迭代快、跨平台强，但体验和系统能力受限。小程序适合平台生态内低成本触达。RN 更适合对体验、性能、原生能力有要求，同时希望复用前端研发效率的场景。选型要看性能要求、动态化诉求、原生能力、团队能力、发布机制和业务生命周期。

2. RN 性能瓶颈一般在哪里？

答题要点：

> 常见瓶颈包括 JS 线程长任务、Bridge 通信频繁、大列表渲染、图片加载、首屏 bundle 体积、动画跑在 JS 线程、原生模块调用过多。优化方向是减少 JS 线程压力、列表虚拟化、图片缓存、bundle 拆分、预加载、使用原生驱动动画、减少跨端通信。

3. AI Coding 如何真正提升研发效率？

答题要点：

> 不能只看“让模型写代码”。更有效的是嵌入研发流程：需求拆解生成技术方案、根据组件规范生成代码、自动补单测、辅助 Code Review、生成迁移脚本、解释线上错误、生成文档。关键是要有规范、上下文、校验和人工 review，否则 AI 代码会引入隐性风险。

4. AI 生成代码如何保证质量？

答题要点：

> 通过类型检查、lint、单测、快照测试、E2E、代码扫描、review checklist、运行时监控来兜底。AI 输出必须进入原有工程质量体系，不能绕过 CI。复杂改动要小步提交和人工确认。

5. 多模态交互前端要考虑什么？

答题要点：

> 文本、图片、语音输入的状态、上传、预览、识别、生成结果展示不同。要考虑权限、文件大小、压缩、上传进度、失败重试、隐私、生成耗时、结果可编辑和用户确认。多模态不是只多一个上传按钮，而是完整交互链路。

**项目包装模板**

> 我可以把自己的 React 复杂工程经验延展到跨端和 AI Coding。复杂业务页面里的模块化、性能优化和工程质量，能迁移到 RN / 小程序的跨端架构；而 AI Coding 方向，我更关注如何把 AI 嵌入研发流程，比如需求拆解、代码生成、单测、Review 和监控，而不是只停留在 prompt 写代码。

## 高频面试题

### 1. 前端接入大模型 API，整体链路怎么设计？

**答题口径**

不要让前端直接拿模型 key 调大模型。常见链路是：

1. 前端提交用户输入、会话 id、业务上下文。
2. 后端做鉴权、权限校验、敏感词和脱敏。
3. 后端组织 prompt、历史上下文、RAG 检索结果或工具调用参数。
4. 后端调用模型，并通过 SSE / WebSocket 流式返回。
5. 前端增量渲染文本、Markdown、代码块、工具调用过程。
6. 最后记录日志、token、耗时、错误、用户反馈，用于监控和评估。

**注意点**

- 模型 key 不能暴露在前端。
- AI 返回内容不可信，不能直接当安全数据源。
- 权限必须在后端做，前端只做体验层控制。
- 要有停止生成、重试、失败兜底、超时和降级。

### 2. 如何实现 ChatGPT 式流式输出？

**答题口径**

前端通常用 SSE 或 WebSocket 接收增量 token。服务端从模型拿到流式输出后，以 chunk 形式推给前端。前端维护一条消息的生成状态，收到 chunk 就追加到当前消息内容里，并触发 UI 更新。

SSE 更适合服务端到客户端的单向文本流，简单、天然支持 HTTP、断线重连成本低。WebSocket 适合双向实时交互，例如多人协作、语音、复杂 Agent 控制流。

**前端状态设计**

- `idle`：未开始。
- `streaming`：生成中。
- `stopped`：用户主动停止。
- `success`：生成完成。
- `error`：生成失败。

**注意点**

- 需要支持 AbortController 或请求取消。
- chunk 可能不是完整 Markdown，要做增量渲染容错。
- 滚动到底部要节流，避免每个 token 都强制布局。
- 生成中按钮状态、输入禁用、停止生成要明确。

### 3. SSE 和 WebSocket 怎么选？

**答题口径**

SSE 是基于 HTTP 的服务端单向推送，适合 AI 文本生成、通知、日志流。实现简单，和普通 HTTP 基础设施兼容好。

WebSocket 是双向长连接，适合强实时双向交互，例如实时协作、语音对话、复杂 Agent 控制、多端同步。

**面试表达**

> 如果只是模型流式输出，我优先选 SSE，因为 AI token 流主要是服务端到客户端，复杂度低，也更容易穿过网关和 HTTP 基础设施。如果需要用户和 Agent 高频双向通信，或者要实时中断、插入指令、多端同步，我会考虑 WebSocket。

### 4. AI 返回 Markdown / JSON 怎么渲染和校验？

**答题口径**

Markdown 渲染要考虑增量内容、代码块未闭合、XSS 和样式隔离。不要直接 `dangerouslySetInnerHTML` 渲染未经处理的内容。需要 Markdown parser、sanitize、代码高亮和错误容错。

JSON 输出要尽量用结构化输出约束，例如 JSON Schema、function calling / tool calling。前端收到后仍然要校验字段和类型，失败时走兜底逻辑。

**注意点**

- 模型输出不是可信输入。
- Markdown 里可能包含危险 HTML。
- JSON 可能不完整、字段缺失或类型错误。
- 增量 JSON 不适合边到边 parse，通常等完成后解析，或服务端输出事件结构。

### 5. RAG 是什么？为什么不用微调？

> 微调相当于让模型去上了一门课，知识已经「内化」到脑子里了。考试的时候是闭卷考试，模型靠「记忆」来回答。但记忆可能会出错，而且新知识需要重新上课（重新训练）。
> RAG 则相当于给模型配了一个参考书架，考试的时候是开卷考试，模型可以翻书找答案。参考书可以随时更新，新增知识不需要重新训练模型。

**答题口径**

RAG 是 Retrieval-Augmented Generation，检索增强生成。基本流程是：把知识文档切块、向量化、存入向量库；用户提问时做 query embedding，检索相关片段，必要时 rerank，然后把相关上下文和问题一起交给模型生成答案。

不用微调的原因是：很多业务知识更新频繁，RAG 更新知识库更快、成本更低、可追溯性更好。微调更适合改变模型风格、格式、特定任务能力，不适合频繁更新事实知识。

**注意点**

- RAG 不是把所有文档塞进 prompt。
- chunk 太大召回不准，太小上下文不足。
- 需要权限过滤，不能检索出用户无权访问的内容。
- 要展示引用来源，降低幻觉风险。

### 6. tool calling / function calling 是什么？

**答题口径**

tool calling 是让模型在需要时输出结构化工具调用请求，而不是直接给最终答案。后端根据模型返回的工具名和参数，执行真实工具，例如查订单、查知识库、创建任务、发起审批，再把工具结果交回模型继续生成。

**典型链路**

1. 用户提问。
2. 模型判断需要调用工具。
3. 模型输出工具名和参数。
4. 后端校验权限和参数。
5. 后端执行工具。
6. 工具结果回传模型。
7. 模型生成最终回答。

**注意点**

- 工具参数必须校验，不能直接信模型。
- 工具执行要有权限、审计、超时和失败处理。
- 高风险操作要用户确认，例如付款、删除、提交审批。
- 前端要展示工具调用过程，让用户知道 AI 在做什么。

### 7. Agent 和普通 LLM 调用有什么区别？

**答题口径**

普通 LLM 调用通常是一次输入、一次输出。Agent 更像一个循环：模型根据目标做计划，选择工具，观察工具结果，再决定下一步，直到完成任务或失败。

常见结构是：

- goal：用户目标。
- plan：任务拆解。
- action：选择工具或回复。
- observation：工具结果。
- reflection / retry：失败后调整。

**注意点**

- Agent 不等于更聪明，复杂度和不确定性更高。
- 要限制最大步数、成本、工具范围和权限。
- 前端要展示过程、进度、可中断和失败原因。

### 8. 如何处理模型幻觉？

**答题口径**

幻觉不能完全消除，只能降低和兜底。

常见手段：

- RAG 提供可靠上下文。
- 要求引用来源。
- 对关键字段做结构化校验。
- 对高风险答案加人工确认。
- 低置信度时拒答或提示不确定。
- 用规则、工具或数据库校验事实。
- 记录用户反馈，用于后续评估。

**面试表达**

> 我不会把模型输出当作绝对事实。业务上要区分低风险生成和高风险决策，高风险场景必须有来源、校验、权限和人工确认。

### 9. token 太长怎么办？

**答题口径**

上下文过长会增加成本、延迟，并可能降低回答质量。处理方式包括：

- 历史消息摘要。
- 滑动窗口保留最近上下文。
- RAG 只取相关片段。
- 删除无关工具结果。
- 大文档先分块检索。
- 对系统 prompt 做压缩。
- 按任务分阶段调用模型。

**注意点**

- 不要把完整聊天历史一直塞给模型。
- 摘要可能丢信息，关键事实要结构化保存。
- 权限信息和用户意图要保留。

### 10. AI 功能如何做监控和评估？

**答题口径**

AI 监控不能只看接口成功率，还要看质量、成本和用户体验。

需要记录：

- 请求耗时。
- 首 token 时间。
- 总生成时间。
- token 输入/输出量。
- 模型和 prompt 版本。
- 工具调用次数和失败率。
- RAG 命中文档和引用。
- 用户点赞/点踩/重试/复制。
- 错误、超时、取消。

评估方式：

- 离线 golden set。
- 人工标注。
- 规则校验。
- LLM-as-judge 辅助评估。
- A/B 实验。

**注意点**

- 日志要脱敏。
- prompt 和模型版本要可追踪。
- 成本要按用户、页面、功能聚合。

## 常见追问

### 1. 前端如何展示 tool calling 过程？

可以把工具调用抽象成事件流：

- `message_start`
- `text_delta`
- `tool_call_start`
- `tool_call_args`
- `tool_call_result`
- `message_end`
- `error`

前端根据事件类型展示不同 UI，例如“正在查询订单”“已找到 3 条记录”“生成最终回答”。这样用户能理解 AI 的工作过程，也方便失败重试和问题定位。

### 2. 如何实现停止生成？

前端可以用 `AbortController` 取消请求。后端收到断开或取消信号后，要中断模型流、停止工具调用或标记任务取消。UI 上把消息状态改成 `stopped`，保留已生成内容，并提供重新生成。

### 3. 如何控制成本？

- 限制 max tokens。
- 压缩上下文。
- RAG 精准召回。
- 低风险任务用便宜模型。
- 高价值任务再用强模型。
- 缓存相同问题或稳定结果。
- 对长任务设置预算和超时。
- 监控 token 消耗和功能 ROI。

### 4. 如何做权限边界？

权限不能靠 prompt 约束。RAG 检索前要按用户权限过滤文档；tool calling 执行前要后端鉴权；高风险工具要二次确认；日志和上下文要脱敏；前端只展示用户有权看到的数据。

### 5. AI 前端和普通前端最大的不同是什么？

AI 输出是不确定的、流式的、可能失败的、可能不可信的。前端要处理生成中状态、部分结果、取消、重试、引用、工具过程、错误兜底和安全展示。普通接口更像确定性数据，AI 更像一个不稳定但有价值的智能服务。
